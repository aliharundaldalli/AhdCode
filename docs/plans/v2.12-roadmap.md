# AhdCode v2.12.0 architecture review and roadmap

**Phase 0 proposal for review**, 2026-11-22. Implementation starts
after the scope is approved. Estimates are engineering effort, excluding
external QA and release approvals.

## Baseline

`e2505f8153c04b319f0dccafa3db4b0713597b50`. The annotated tag object is

## Architecture and findings

| Area | Current architecture | Evidence and v2.12 implication |
| --- | --- | --- |
| Compiler and language | One frontend resolves modules and required files, lexes and parses source, and performs static semantic analysis. Native builds lower the checked graph to validated IR, generate Go, and build it in a temporary workspace. | The specification header names v2.9.0 while later conformance tests and release behavior exist. Audit a small set of rules against implementation and tests, then update the spec's coverage statement. Preserve explicit nullable types, overload and default-argument resolution, and published diagnostic codes. [Pipeline](../../internal/build/pipeline.go) · [Specification](../../AHDCODE_LANGUAGE_SPEC_v0.1.md) |
| Runtime and standard library | Builtins have compiler-owned interfaces consumed by analysis. Declarations, evaluator dispatch, lowering, and Go runtime behavior remain separately testable. First-party `.ahd` modules are embedded. Native programs embed selected runtime source, and some features use packaged helpers. | Validate new builtins end to end. Reuse shared driver/runtime operations and the current helper boundary. Include failure types and lifecycle observable by callers in parity tests. [Builtin interfaces](../../internal/semantic/standard_modules.go) · [Embedded framework](../../internal/framework/framework.go) · [Runtime embedding](../../internal/backend/golang/ahdruntime/embed.go) |
| Database APIs | SQLite uses one logical connection per handle inside the long-lived `ahdsqlite` helper. MySQL uses `database/sql` pooling and PostgreSQL uses its separate pgx-backed runtime. All support bound parameters and explicit transactions, with driver-specific results and semantics. | SQLite currently opens read-write/create and configures a fixed five-second busy wait. The backup path has a Windows QA failure. Helpers and user code receive DB errors through a text message. PostgreSQL has required live CI, and equivalent MySQL service coverage is missing. [SQLite helper](../../cmd/ahdsqlite/main.go) · [SQLite protocol](../../internal/sqliteproto/sqliteproto.go) · [MySQL](../MYSQL.md) · [PostgreSQL](../POSTGRESQL.md) |
| Database workflow | The migration runner targets SQLite and owns transaction/history protection. Database-backed starters support SQLite or MySQL. PostgreSQL is a usable module for application code. | State the coverage difference explicitly. Keep migration locking, rollback and checksum behavior intact. A server migration runner would need a separate design for DDL, locking, credentials, and recovery. [Migration runner](../../internal/migrate/migrate.go) · [Starter options](../../internal/initweb/options.go) |
| Web framework | Web wraps HTTP and Web.UI builds escaped HTML nodes. The CLI watches the `.ahd` dependency graph. Development HTTPS, persistent sessions, PWA support, and deployable Web packages are shipped. | Keep .ahd + Web.UI and the removed Templates boundary. Carry existing HTTP/WSS shutdown, SQLite session ownership, production proxy, and isolated service-worker cache cases forward as regressions. Keep the PWA's same-origin scope and public-only cache policy. [Web guide](../WEB.md) · [PWA policy](../PWA.md) · [Templates migration](../UPGRADE_2.11.md) |
| CLI, editor, and performance | The CLI exposes `build`, `run`, `dev`, `format --check`, and `lsp`. LSP diagnostics use the compiler frontend. The bounded native run cache skips the Go build on hits and still runs frontend compilation. LSP uses full-document sync and can compile unopened entries for workspace queries. | There is no standalone semantic `check` command or machine-readable compiler diagnostic output from the CLI. Repeated editor analysis is a concrete cost candidate. The current review found specialized benchmarks but no matching edit-to-diagnostic/build-stage baseline, so the payoff of changes remains unmeasured. [CLI dispatch](../../cmd/ahdcode/main.go) · [Run cache](../../internal/build/runcache.go) · [Workspace analysis](../../internal/analysis/workspace.go) · [LSP docs](../LSP.md) |
| Documentation and test architecture | Canonical guides are paired with Turkish docs where present. Generated starters embed an English snapshot with drift tests. Coverage spans compiler stages, native and evaluator paths, platform processes, Node worker tests, and service-backed CI. | Keep `docs/` and exported starter docs aligned. Prior broad Windows QA recorded extensionless executable fixtures, symlink privilege limits, path and mode assumptions, and a SQLite backup drive-path failure. Triage fixtures separately from product regressions. Current CI is configured for pushes to `main` and the old RC branch and PRs to `main`. [Bundle checks](../../internal/initweb/docbundle_test.go) · [Phase 7 QA](../qa/v2.11/phase-7.md) · [Workflow](../../.github/workflows/ci.yml) |

The organizing goal is to make AhdCode applications easier to check, operate,
and measure on the architecture that shipped. Keep the frontend authoritative,
the database handles driver-specific, and Web behavior compatible with v2.11.
The [3.0 roadmap](../../ROADMAP_3.0_TR.md) records earlier proposals for an
in-process runtime and mobile targets. Evidence from this cycle may inform
those designs, which require their own approval.

## Prioritized implementation phases

### Phase 1 · Establish regression and performance baselines

| Priority and work | Motivation and design | Compatibility and dependencies | Tests and exit criteria | Estimate |
| --- | --- | --- | --- | --- |
| P0 · Platform regressions | Reproduce and classify Windows failures against the tag. Fix test launch paths through the existing executable-path policy. Check symlink preconditions only in fixtures that genuinely require them. Record the tagged CI matrix and propose development or RC CI coverage without adding a publishing workflow. | No public API changes. Preserve actual reparse/junction coverage and distinguish unsupported privilege from validation failures. Requires Windows plus one case-sensitive host. Review the post-tag docs and Studio fixes before broader acceptance. | Run the Windows relocation and resource fixtures in normal and race mode. Preserve Linux and macOS process, session, and packaging checks. Publish names of failures, skips, and ownership. | Small–medium, 3–5 days |
| P0 · Bound workspace discovery | The Windows references test timed out while walking directories from a volume root. The current candidate-file cap can still leave directory traversal running. Correct OS-aware root detection, stop traversal when the cap is reached, and define a directory-entry budget for large sparse trees. | Keep the LSP wire contract and open-document precedence. Explicit project directories retain documented discovery. Review the behavior at any budget limit so rename does not silently treat a partial search as complete. Requires Windows and Unix path fixtures. | Exercise implicit volume roots, ordinary workspace roots, large sparse trees, and budget exhaustion. Verify references and rename within the approved scope, including open buffers and symlink fixtures. | Medium, 2–5 days |
| P0 · Reproducible measurement | Time module loading/semantic analysis, lowering and Go emission, workspace staging, Go build, and child readiness separately. Measure LSP edit-to-diagnostics and repeated references, and SQLite open/query cost with synthetic data. | No public timing API. Reuse existing caches and measure with separate scratch state. Record Go version, OS, hardware, fixture counts, and cache conditions. | Small program, generated Basic plus SQLite fixture, and a medium multi-file workspace. Record cold/warm medians and p95 over at least 20 comparable samples and allocations where Go benchmarks apply. Repeat noisy results before selecting an optimization. | Medium, 3–5 days |

Baseline timing should separate a warm Go cache from an enabled AhdCode run
cache. `AHDCODE_NO_RUN_CACHE=1` disables the latter. Use an isolated Go cache
for cold measurements. Compare the same fixture and machine and verify that
outputs and diagnostics match. Keep timing variability out of mandatory CI
pass thresholds until repeatability is established.

### Phase 2 · Make database workflows predictable

| Priority and work | Motivation and proposed API | Compatibility and dependencies | Tests and exit criteria | Estimate |
| --- | --- | --- | --- | --- |
| P0 · SQLite backup reliability | Resolve the reproduced Windows drive/URI issue. Keep `Database.backupTo(path)`, consistent snapshots, atomic no-overwrite publication, and error class. Investigate the helper path handling before changing the DB runtime. | Preserve existing backup files, transaction restrictions and cleanup. Reuse the current backup implementation and supported SQLite dependency. | Verify a live WAL snapshot and restore, Unicode/spaces, platform path handling, conflicts, and partial-file cleanup. Run the same fixture via helper, native, and evaluator where applicable. | Medium, 3–6 days |
| P1 · Explicit SQLite opening policy | Proposed `SQLite.openWithOptions(path: String, readOnly: Bool, busyTimeoutMilliseconds: Int) -> Database`. Keep `SQLite.open(path)` and its five-second behavior. Validate a bounded timeout. Zero means no lock wait. Open an existing DB with SQLite's read-only mode and fail for nonexistent files or a read-only `:memory:` request. | Use a new helper operation so an old helper cannot silently ignore read-only. Provide a clear helper-version error and keep old callers working with the existing operation. Preserve bound values, one-connection semantics, transactions, existing SQLite error identity, and persistent session defaults. Review allowed filesystem/URI forms before exposing options. | Test packaged helper discovery and mismatches, failure to create or write in read-only mode, writer contention and timeout expiry, valid bound queries, alias/close behavior, and parity across semantic analysis, LSP, REPL and native builds. | Medium, 5–8 days |
| P1 · MySQL live acceptance and driver contract | Add isolated MySQL service coverage for the runtime, native/evaluator parity, and the generated MySQL starter. Publish a driver behavior matrix for result types, timeout, rollback, close, and binary handling. Keep driver-specific APIs and SQL. | No new connection flags, driver dependencies, or network defaults. Test credentials belong only to the disposable service. Retain PostgreSQL service coverage and SQLite migration semantics. | Verify binding and rollback, affected rows and IDs, duplicate labels, connection failure redaction, and concurrent use of separately acquired transactions. A configured service job must detect fixtures skipped unexpectedly. | Medium, 4–7 days |

This phase prioritizes safe use of the existing database APIs. SQLite BLOB
round trips, stable programmatic error metadata, and bounded or streaming
result sets are real gaps. BLOB behavior crosses the helper wire format.
Typed DB errors cross both native and evaluator error representations.
Streaming introduces cursor lifetime and cancellation contracts. These
belong to follow-up proposals with real application examples.

### Phase 3 · Improve developer feedback and language consistency

| Priority and work | Motivation and proposed API | Compatibility and dependencies | Tests and exit criteria | Estimate |
| --- | --- | --- | --- | --- |
| P1 · Standalone checker | Proposed `ahdcode check <entry.ahd> [--format text\|json]`. Use module resolution and semantic analysis without generating Go, executing programs, or requiring native helpers. In JSON report a schema version and stable severity, code, message, path/range, and optional hint. Define range units explicitly. | Additive command. Keep `format --check`, `build`, and LSP output as shipped. Proposed exit codes are 0 for success, 1 for check/input errors, and 2 for usage. JSON output must stay separate from process logs and omit source excerpts by default. | CLI snapshots for valid, invalid, missing require, warning-only, and invalid argument cases. | P1 · Targeted language conformance | Pin existing rules for nullable narrowing, numeric widening/overload ranking, default arguments, and inferred callable signatures. Any observable correction needs a minimal reproduction, normative reference, compatibility decision, and migration note when relevant. Keep the authoritative frontend and existing test layers. | Compile accepts/rejects with stable codes, native/evaluator values and error classes, formatter round trips, and LSP hover/signature positions for Unicode and CRLF. ### Phase 4 · Make one measured performance improvement

**P2, medium, 4–8 days, conditional on Phase 1 results.** The first candidate
is repeated LSP workspace analysis. If profiling confirms repeated work,
evaluate a small in-memory snapshot reuse policy keyed by content and
dependencies. Maintain open-overlay precedence, explicit closure and
invalidation, bounded memory, and existing UTF-16 positions. Another
candidate is temporary Go workspace staging on genuinely cold builds if
measurements show it dominates. Select one and leave the other in the
backlog. Existing caches and the toolchain path remain supported.

Require unchanged correctness and a reproducible improvement on an agreed
user-visible fixture before shipping. Start with a target of at least
15% lower median for the selected operation with no material p95 or memory
regression, and record the before/after measurements. Test source creation,
deletion, edits during analysis, failed dependencies, and invalidation for
any reused result. Run concurrency tests under `-race`. If profiling
does not find a worthwhile small change, publish the measurements and move
to release QA. A persistent index, incremental compiler, or shared in-process
runtime needs a separate design and explicit approval.

### Phase 5 · Cross-platform release QA and documentation

**P0, medium, 3–5 days.** Validate actual source and toolchain packages and a
separately packaged Web application. Keep production settings, endpoints,
and signing workflows untouched during development. Align the changelog,
canonical guides, installer docs, and generated starter snapshot with the
approved scope. Build on Windows x64, Linux x64, and macOS ARM64 and record
which other architectures were cross-compiled or run natively. Use the
existing signing and checksum policy for whatever artifacts are eventually
authorized. Run existing HTTP/WSS shutdown, persistent session, live reload,
relocated Web package, and worker/browser checks on the release candidate.
Record skipped cases and compare performance to Phase 1. Release judgment
requires passing the required targeted suites and a separate review of any
outstanding baseline failures.

## Deferred scope

| Candidate | Earliest review | Reason or prerequisite |
| --- | --- | --- |
| SQLite BLOB bind/read, structured DB errors, and streaming/bounded results | v2.13 | Gather use cases first. Specify representation, size limits, helper skew behavior, redaction, and cursor ownership before expanding any driver contract. |
| PostgreSQL starter or network-driver migrations | v2.13 | Establish reproducible live driver tests. Keep the SQLite history format stable and design engine-specific locks, transactional DDL, failure recovery, and credential handling. |
| Common DB abstraction, ORM, query builder, or broad pool/transaction API | v2.13 or later | Existing transaction and error behavior differs. A shared abstraction needs evidence from applications using multiple engines. |
| Project-wide persistent index, incremental frontend, debugger/DAP, new language constructs | v2.13 or later | Require conformance, demand, and profiling evidence. An index or frontend redesign requires an approval gate. |
| New in-process target, mobile packaging, authenticated offline data, or sync | v3.0 planning or later | These entail new runtime, packaging, and data lifecycle contracts. Preserve the current process and Web/PWA model throughout v2.12. |

## Phase 0 verification

On Windows amd64 with Go 1.26.7, the local ordinary sample passed for
`internal/module`, `internal/semantic`, `internal/analysis`,
`internal/formatter`, and `internal/migrate`. The broad LSP test process
was stopped after it ran for more than two minutes. An isolated references
test then reached its 15-second timeout. The stack shows
`Store.workspaceSourceFiles` in `filepath.WalkDir` reading deeply nested
Windows directories. The file URI fixture has no project workspace, so
this is a useful regression case for the volume-root guard.

~~~powershell
$env:GOFLAGS='-buildvcs=false'
go test -count=1 ./internal/module ./internal/semantic ./internal/analysis ./internal/lsp ./internal/formatter ./internal/migrate
go test -v -count=1 -timeout 15s -run '^TestReferencesExcludesDeclarationByDefault$' ./internal/lsp
~~~

Both SQLite backup tests below failed on Windows amd64 with the
`CreateFile /C:` drive-path error on the tagged release. The live-snapshot
test also reported helper cleanup denied on that run. These are v2.11.0
baseline observations. The release workflow ran a focused Windows selection.

~~~powershell
go test -v -count=1 -run '^TestSQLiteBackup(IsAConsistentLiveSnapshot|FailuresLeaveNoBackup)$' ./internal/backend/golang/ahdruntime
~~~
